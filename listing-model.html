Rumee — Listing Tab

A safe place to archive a listing template, building toward filling it in for you

IN PROGRESS
2026-07-28

Flipkart's bulk-listing template has no API path at all — creation only happens through the Excel file you download from Seller Hub. This tab exists to make that file safer and faster to work with, one careful piece at a time, without ever risking the "sensitivity" of the template itself — its macros, dropdowns, and validation.

built and live designed, not built yet
01

Design + Variation is a real dropdown, never free text

Picked straight from Product Master, with a "+ Add new…" option that goes through the same trusted, duplicate-proof creation path Reassign and Rename already use. A typo or near-miss spelling can no longer create a listing folder with no real product behind it — that exact failure mode had already fragmented the catalog once before, for a different feature, before this fix.

02

Seller SKU ID collision check

Flipkart has no API to validate a SKU ID against, so this checks it against every SKU ID this catalog has ever recorded instead — live warning while typing, hard block on submit. It only catches a SKU ID reused from an existing listing; it can't catch every reason Flipkart might reject a brand-new one.

03

The file is archived byte-for-byte, never opened

Two approaches were tested and rejected before this one: editing the file with a Python library lost 55% of its content (the dropdown bindings and any embedded macro); a service-account Drive upload failed outright (bare service accounts have no storage quota of their own to create files with). The file now goes straight into your own Drive, under your own OAuth sign-in, completely unmodified.

04

Fixed Content

A toggle + value for every column that stays the same across your whole catalog (Brand, HSN, Country of Origin, etc.) — you decide what counts as fixed, not a guess made on your behalf. Anything left off is asked for on every listing instead.

The same screen also decides which section of the New Listing form each field will appear in — a sensible default grouping to start (Pricing, Product Identity, Materials, Gemstones, Dimensions, Images, Warranty, Description), but any field can be moved to a different section if that fits your own workflow better.

05

Resuming an interrupted listing

Typing a SKU ID that already has a draft shows a banner immediately — status, last-updated date, and a link to the file already archived for it — before you ever reach the upload button. Uploading again for that same SKU requires an explicit confirm, since it adds another copy to the same Drive folder rather than replacing anything. Nothing already saved against that SKU is ever silently overwritten.

That check has three real outcomes, not just yes/no: a file that's genuinely gone (permanently deleted) is skipped silently, since there's nothing left to duplicate — but a file sitting in Google Drive's Trash is treated as its own case, asked about explicitly rather than assumed either way. Choosing to proceed leaves the trashed file exactly as it is and archives a fresh copy in the real folder instead; it never tries to restore or reopen anything from Trash. Whichever path is taken, the "open the archived file" link always ends up pointing at the most recently uploaded file sitting in the actual folder — never at Trash, and never at something stale.

That yes/no decision is asked inside the dashboard itself, styled to match everything else here — not a native browser popup.

06

Drive connects once, not every visit

The Google OAuth Client ID is saved once, ever, on a browser (and reused automatically if Returns tab's own Drive setup already saved one). After that, nothing needs an explicit "Connect" click on return visits — the actual access token is acquired silently in the background right when it's needed, the same way Google's own sign-in already stays valid across sessions until you actually revoke it.

07

The field-value form

The actual "give minimal input, get the values back" piece — every non-fixed column, one section at a time (Pricing, Product Identity, Materials, Gemstones, Dimensions, Images, Warranty, Description), using whatever grouping Fixed Content has configured. Dropdown-constrained wherever the template defines allowed values, with real multi-selects (not hand-typed "::" separators) for the columns that allow more than one value.

Pre-fill priority: whatever's already saved against this exact SKU first (resuming), then the most recent accepted listing of the same design+variation, then blank. Progress saves every time you move between sections, not just on a final submit — the "Continue filling details" link on an existing draft jumps straight back into the form without needing to re-upload anything.

08

CSV export

Not built yet. Takes whatever's filled in the form and gives you a row, in the template's exact column order, to paste directly into your real file.

09

Rejection / fix-recording loop

Not built yet. Paste Flipkart's rejection reason in, get a corrected value back, and only the value Flipkart actually accepted becomes what future listings of the same design reuse — never a value that already failed once.

Worth knowing

Only Flipkart is built. Meesho and Amazon are planned for this same tab later — the columns and rules will differ per platform, so each gets its own template analysis when the time comes.

rumee_fk_listing_config and rumee_fk_listing_specs need their Firestore rules published from the Firebase Console before Fixed Content or draft-resuming will work — the archive-to-Drive step doesn't depend on this and works independently.
