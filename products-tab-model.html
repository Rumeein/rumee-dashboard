Rumee — Products Tab

The catalog's own control surface

LIVE
2026-07-24

This page covers the Products TAB's own UI -- filters, the Needs Review queue, Classify Products. For the underlying Design → Variation → Listing data model itself, see How Things Move, which already owns that story.

the tab's own render/write steps what fills in once BOM data resolves
01

Public catalog, private BOM overlay

product_master is fully public-read, so the whole catalog paints instantly for anyone. The green "✓ BOM" / neutral "No BOM" chip per variation only fills in afterward, once the sign-in-gated rumee_boms fetch resolves -- an anonymous viewer sees the full catalog first, cost/BOM info arrives a moment later.

02

Filters -- one single-select, two independent add-ons

Status filters (Needs attention / All / Active / Out of stock / Inactive / No BOM) are mutually exclusive, but Stock Min–Max range and No URL are always-additive layers on top of whichever single-select is active -- so you can combine "No BOM" with "stock between 0 and 10" in one view.

03

Needs Review -- a real, ordered write sequence

Assigning an unmapped listing writes pm_overrides FIRST (so the sync pipeline won't recreate the same unresolved entry), THEN appends the listing into the target Product Master doc, and only THEN deletes the needs_review entry. If anything fails partway, the mapping decision already exists -- nothing has to be redone from scratch.

04

Classify Products -- suggests, never auto-applies

A separate queue lists every product missing a Product Type, or whose variation doesn't match its type's allowed list. Each row gets a suggested type from a matcher function, but nothing is ever silently applied -- picking the suggestion (or a different one) is always a deliberate, explicit action.

Worth knowing

The "BOM / No BOM" chip is keyed by the Product Master document's real Firestore id, not its own sku_id field -- those two values only coincidentally match for single-word designs. This was a real, fixed bug (78 of 84 products briefly showed "No BOM" incorrectly) -- if a BOM link ever looks wrong again, that key mismatch is the first thing worth checking.
