Rumee — Data Pipeline Tab

One file, two different kinds of "fresh"

LIVE
2026-07-24

This tab reads three plain JSON files straight from the public GitHub repo -- no Firestore involved. The trickiest thing to understand is that one of those files mixes a per-run snapshot with rolling historical state in the same document.

the pipeline / the tab itself
01

Last Run Health -- a snapshot, not a log

The errors/warnings arrays inside pipeline_run_log.json are emptied at the start of every single run and fully overwritten at the end -- they reflect only the MOST RECENT run, nothing before it. A green "All Good" badge means the last run was clean; it says nothing about yesterday.

This is exactly why an item disappearing on its own next run means it fixed itself, while an item that reappears every run is a real, ongoing failure -- not stale noise to dismiss.

02

The Pipeline Map -- the OTHER half of the same file

Right below the health badge, the same JSON file also carries stream_dates/stream_gaps/stream_status/stream_rows -- these ARE computed from the full historical database, not just the latest run, and feed the four-column Pipeline Map table (Data Stream / Extension Generates / Pipeline Processes / Vantage Agent Uses), grouped by platform, with gap-date chips for any missing-day ranges.

03

Manifest Reliability -- catching the OTHER kind of failure

This cross-check compares what the rumee-auto-sync browser extension itself claims it uploaded to Drive against what the pipeline actually ingested -- a mismatch here points at a silent EXTENSION failure, not a pipeline failure, which is a genuinely different thing to go fix.

04

Wishlist

A small card listing data Vantage (the AI advisor) would like but doesn't have yet -- hidden entirely when empty, its count mirrored onto the nav tab's own badge so you know there's something here before even opening the tab.

Worth knowing

A client-side "dismiss this warning" feature was deliberately never built for the per-run errors/warnings -- it would only hide the message on one browser/device and risks masking a real ongoing failure. If something needs suppressing permanently, that has to be a server-side skip-list in process.py for specific, individually-confirmed-dead files, not a local hide.
