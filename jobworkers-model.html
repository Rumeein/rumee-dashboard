Rumee — Job Workers Tab

One assignment, a running story of returns

LIVE
2026-07-26

A job assignment is created once, then its story is told entirely by an append-only list of returns logged over time. There's no upfront pieces target -- the assignment is tied to a real BOM'd product instead, so expected yield, material remaining, and payment owed can all be worked out from the material given, and are recomputed fresh every time, never stored.

the write actions / the always-fresh summary
01

An assignment is created once

Date, worker, an Output product picked from Product Master (only products that already have a BOM show up -- the BOM is what makes everything below possible), rate per piece, and a Materials Given table -- created as status: open with an empty returns array. There's deliberately no quantity-assigned field: you don't know how many pieces will come back until the worker returns them. Nothing here changes after creation except through Log Return or Close/Reopen.

02

Log Return -- qty 0 is a valid, useful entry

A return with 0 pieces returned but a payment amount is exactly how an advance gets logged -- no separate "advance" action exists, it's just this same form with qty left at 0. The payment field auto-suggests qty × rate but stays fully editable. A live re-fetch of the assignment happens right before writing, so two returns logged close together don't silently clobber each other.

03

One action, up to three writes

Logging a return can cascade: (1) append to returns[] always, (2) if the assignment was closed, a separate write reopens it (Firestore rules only allow touching returns OR status per update, never both at once), (3) if a payment amount was entered, a mirrored entry gets created in Purchases (category "Job Work") with back-references to this assignment and return -- so total cash-out reports never miss a job-worker payment.

04

Balance and materials-remaining are never stored

Every number in the Worker Summary is computed fresh, every render, straight from the assignment doc plus its returns array: work value = returned qty × rate; balance = total paid minus work value (positive means the worker still owes you an advance, negative means you still owe them for completed unpaid work); materials remaining = material given minus what the BOM says the returns-so-far should have consumed. Nothing drifts out of sync because nothing is cached.

05

Expected Yield & Variance -- flagged for every assignment, not just the bad ones

Expected Yield = the most pieces the material given could produce, per the output product's BOM (the ingredient that runs out first sets the ceiling). Variance = pieces actually returned minus that expected number. Every assignment shows both, in the Assignments table and in a dedicated Yield Review section sorted worst-variance-first -- nothing is filtered out or hidden behind a tolerance, so the whole history is there to review and refine the BOM against over time.

06

Closing warns you first

Closing an assignment while material is still outstanding (per the BOM-derived remaining calculation) shows an explicit warning naming the exact amounts, since closing removes them from the running summary totals.

Worth knowing

There's no way to edit materials_given, product_master_id, or rate_per_piece after creation -- those are locked by design once the assignment exists, matching Firestore rules that only allow touching returns or status.
