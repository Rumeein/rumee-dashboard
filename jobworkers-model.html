Rumee — Job Workers Tab

One assignment, a running story of returns

LIVE
2026-08-05

A job assignment is created once, then its story is told entirely by an append-only list of returns logged over time. There's no upfront pieces target -- the assignment is tied to a real BOM'd product instead (sellable or an in-house component), so expected yield, material remaining, and payment owed can all be worked out from the material given. Material stock moves for real the moment you save -- this tab replaced the old Materials-tab "Conversion Batches" entirely (2026-07-27), gaining real stock/cost integration plus everything Conversion Batch could already do, in-house work included.

the write actions / the always-fresh summary

The diagram above is the original 2026-07-27 create-and-return flow. Four more write paths were added 2026-08-05 — BOM auto-fill, Edit Return, Return Unused Material, and Edit Assignment — covered in stages 08–11 below, not yet redrawn into the picture.

01

An assignment is created once

Date, an optional Job Worker (leave blank for in-house work), an Output picked from either Product Master (sellable items) or Item Master (components/in-house intermediate items) -- only products that already have a BOM show up, the BOM is what makes everything below possible -- rate per piece, and a Materials Given table. There's deliberately no quantity-assigned field: you don't know how many pieces will come back until they're returned.

02

Saving consumes real material stock, right then

Every material in Materials Given is consumed from stock immediately via the same FIFO lot system as Purchases/QC/Stock Adjust -- it physically left the warehouse the moment it was handed over (or set aside for in-house work), so the software reflects that right away, not later when it's returned as finished pieces. The REAL cost that consumption returns (not a guess) is used to work out an Expected Yield from the BOM, then frozen onto the assignment permanently as material_cost_total, expected_yield, cost_per_piece, and a snapshot of the BOM ratios used -- a later edit to the standing BOM never silently changes what an already-saved assignment shows. If none of the materials given match the BOM's ingredients, the save is blocked before anything is touched.

03

Log Return -- qty 0 is a valid, useful entry

A return with 0 pieces returned but a payment amount is exactly how an advance gets logged -- no separate "advance" action exists, it's just this same form with qty left at 0. The payment field auto-suggests qty × rate but stays fully editable. A live re-fetch of the assignment happens right before writing, so two returns logged close together don't silently clobber each other.

04

One action, up to four writes

Logging a return can cascade: (1) append to returns[] always, (2) if the assignment was closed, a separate write reopens it (Firestore rules only allow touching returns OR status per update, never both at once), (3) for a component/in-house output, real finished-piece stock is posted using the cost/piece frozen at creation, routed to the QC-pending bucket if that material type requires it (same check a purchase of that type gets) -- a sellable-product output has no manually-writable stock in this app at all (platform-synced), so there's nothing to post for those, Expected Yield/Variance IS the record, (4) if a payment amount was entered AND there's a real job worker (not in-house), a mirrored entry gets created in Purchases (category "Job Work") -- so total cash-out reports never miss it.

05

Expected Yield & Variance -- flagged for every assignment, not just the bad ones

Expected Yield = the most pieces the material given could produce, per the BOM ratios frozen at creation (the ingredient that runs out first sets the ceiling). Variance = pieces actually returned minus that expected number. Every assignment shows both, in the Assignments table and in a dedicated Yield Review section sorted worst-variance-first -- nothing is filtered out or hidden behind a tolerance, so the whole history is there to review and refine the BOM against over time.

06

Balance and materials-remaining, computed fresh from frozen numbers

Every number in the Worker Summary is computed fresh, every render, from the assignment's own frozen fields plus its returns array: work value = returned qty × rate; balance = total paid minus work value (positive means the worker still owes you an advance, negative means you still owe them for completed unpaid work); materials remaining = material given minus what the frozen BOM snapshot says the returns-so-far should have consumed. Nothing here re-reads the live/current BOM.

07

Closing warns you first

Closing an assignment while material is still unaccounted for (per the frozen-BOM remaining calculation) shows an explicit warning naming the exact amounts, since closing removes them from the running summary totals.

08

New: picking an Output pre-fills Materials Given (2026-08-05)

Picking a BOM'd Output on the New Assignment form now fills the Materials Given table straight from that BOM's own components, qty defaulted to the per-unit ratio (there's still no pieces-target field here, so per-unit is the only sensible starting number) -- every row stays freely editable/scalable from there, same as typing one in by hand.

09

New: Edit Return -- corrects a mistake without replaying creation (2026-08-05)

Every logged return in the History panel now has an Edit button. It corrects that entry's date/qty/amount/notes in place -- but deliberately does NOT re-run everything Log Return originally did (that would double-consume stock and double-pay). Instead it reconciles only the delta: a qty change posts one compensating stock movement for the difference, an amount change updates the already-mirrored Purchases entry for that return.

10

New: Return Unused Material -- a real event, not a guess (2026-08-05)

Before this, "material still with them" was pure inference (given minus what the BOM says the returned pieces should have used) -- there was no way to record a worker physically handing back leftover raw material unused. The Return Material button opens a form listing every material still outstanding on the assignment, one qty box each; fill in as many as apply and Save logs all of them in one action, restocking each at the exact cost it was taken out at. A new History table shows the running Given / Used / Returned Unused / Remaining per material.

11

New: Edit Assignment -- and the one thing it still won't let you touch (2026-08-05)

An Edit button on every assignment row opens the same New Assignment form, pre-filled, for correcting date/worker/output/rate/materials after the fact -- something the section below used to say was impossible by design. Changing a material's qty is checked against what's already been consumed by returns or handed back unused before the save is allowed to go through at all. Output Product is the one field that locks the moment any return or material-return exists against the assignment -- its BOM snapshot and any finished-goods stock already posted are tied to that original output, so changing it afterward would leave that history pointing at the wrong product.

Worth knowing

Superseded as of 2026-08-05: earlier versions of this page said materials_given/output_id/rate_per_piece could never be edited after creation. That's no longer true -- stage 11 above (Edit Assignment) covers all of it, with Firestore rules widened three times the same session to permit it. Only Output Product still locks, and only once the assignment has real history against it.

This tab replaced the Materials tab's old "Conversion Batches" feature entirely (2026-07-27) -- everything it could do (in-house work, component/intermediate output) now lives here too, plus multi-partial-return tracking and Expected Yield/Variance analysis it never had. Historical rumee_conversions data and the stock it already moved are untouched in Firestore, just no longer added to.

A real naming-mismatch bug was found the same day these edit features shipped: materials_given rows are matched to the BOM by exact name, so a material named slightly differently from its own BOM ingredient (e.g. "S Hook" vs "S-Hook (Golden)") silently looked fully unconsumed no matter how many pieces had come back. Now flagged wherever Remaining is shown instead of trusted blindly. If it happens again, the Materials tab's "Usage" button (on any item) shows everywhere that material is referenced, and "Merge" folds a genuine duplicate into the correct one -- BOMs, assignments, purchases, and stock all follow, without voiding either record for you.
